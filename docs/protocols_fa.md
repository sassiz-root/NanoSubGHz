# پروتکل‌های OOK در باند Sub-GHz — مرجع فنی

درک طرح‌های رمزگذاری مورد استفاده در کنترل‌های از راه دور، ریموت‌های
خودرو و سنسورهای مصرفی باند ۳۱۵/۴۳۳ مگاهرتز.

این سند دو خانواده رایج **کد ثابت** را پوشش می‌دهد:
**PT2262/PT2260/PT2264** و **EV1527/HS1527**، به‌همراه مقایسه با
سیستم‌های Rolling Code.

---

## ۱. مروری بر ASK/OOK در Sub-GHz

**ASK** (Amplitude Shift Keying) و پسر عموی ساده‌ترش **OOK**
(On-Off Keying) یک حامل را با روشن/خاموش کردن مدوله می‌کنند:

```
داده:     1  0  1  1  0  1  0
حامل:     █  _  █  █  _  █  _   (روشن=1، خاموش=0)
```

گیرنده الگوی روشن/خاموش را می‌بیند و بیت‌ها را بازسازی می‌کند.
**هیچ کلاکی ارسال نمی‌شود** — گیرنده باید زمان‌بندی را از عرض پالس‌ها
استنباط کند.

**فرکانس‌های رایج:**
- **۳۱۵ مگاهرتز** (آمریکای شمالی، ژاپن، برخی نقاط آسیا)
- **۴۳۳.۹۲ مگاهرتز** (اروپا، ایران، بیشتر نقاط جهان)
- **۸۶۸ مگاهرتز** (اتحادیه اروپا، تجهیزات کوتاه‌برد)
- **۹۱۵ مگاهرتز** (قاره آمریکا، باند ISM)

**زمان‌بندی:**
- عرض پالس OOK معمولاً **۲۰۰ تا ۵۰۰ میکروثانیه**
- یک فریم معمولاً **۱۲ تا ۳۲ بیت** (به‌علاوه Sync)
- پیام کامل هر **۲۰ تا ۱۰۰ میلی‌ثانیه** برای اطمینان تکرار می‌شود

## ۲. PT2262 / PT2260 / PT2264 (Princeton / «کلاسیک»)

**PT2262** یک رمزگذار کم‌هزینه از Princeton Technology است (بعدها توسط
بسیاری از تولیدکنندگان کلون شد: EV1527، HS1527 و غیره). این خانواده
**غالب** در کنترل درب پارکینگ، ریموت‌های ارزان و زنگ‌های بی‌سیم درب
در سراسر جهان است.

### ۲.۱ ساختار فریم

فریم PT2262 عبارت است از:

```
[Sync] [Bit1] [Bit2] ... [Bit12..24] [Sync?]
```

هر فریم شامل **۸ تا ۲۴ بیت داده** است (معمولاً ۱۲ برای رمزگذارهای
۱۲ بیتی و ۲۴ برای رمزگذارهای ۲۴ بیتی).

### ۲.۲ رمزگذاری (سه‌گانه)

هر بیت به‌صورت **جفت پالس** با چرخه کاری متفاوت رمزگذاری می‌شود:

| نماد | معنا | زمان‌بندی |
|---|---|---|
| **`0`** (کوتاه-کوتاه) | بیت پایین | ▄▄ `_` ▄▄ `_` |
| **`1`** (بلند-کوتاه) | بیت بالا | ▄▄▄▄ `_` ▄▄ `_` |
| **`f`** (کوتاه-بلند) | **شناور / سه‌حالته** | ▄▄ `_` ▄▄▄▄ `_` |

که در آن `▄▄` ≈ **α** (پالس کوتاه)، `▄▄▄▄` ≈ **3α** (پالس بلند) و
فاصله همیشه ≈ **α** است.

مقدار معمول **α ≈ ۳۵۰ میکروثانیه** برای ریموت‌های ۴۳۳ مگاهرتز
(بین ۱۵۰ تا ۵۰۰ میکروثانیه متغیر است).

### ۲.۳ پالس Sync

بین فریم‌ها، یک **پالس Sync بلند** ظاهر می‌شود: `▄` + فاصله بلند ≈
**31α** (یا 32α در برخی چیپ‌ها). Sync نشان‌دهنده «شروع فریم جدید» است.

### ۲.۴ آدرس در برابر داده

در سیستم‌های مبتنی بر PT2262:

- **N بیت اول** = **آدرس** (ثابت برای هر ریموت؛ همان «کد خانه»)
- **M بیت آخر** = **داده** (دکمه‌ها / وضعیت)

برای ریموت ۱۲ بیتی:
- ۸ بیت آدرس (کلیدهای DIP) + ۴ بیت داده (دکمه‌های A/B/C/D)
- تقسیم رایج: **۱۰ آدرس + ۲ داده**، یا **۸+۴**

برای ریموت ۲۴ بیتی:
- ۲۰ آدرس + ۴ داده (معمول)

**آدرس از طریق کلیدهای DIP قابل تغییر است** (2^8 = ۲۵۶ ترکیب). اگر
یک ریموت دوم برای همان درب می‌خرید، کلیدهای DIP آن را با ریموت اصلی
یکسان می‌کنید.

### ۲.۵ مثال رمزگذاری (۱۲ بیتی، آدرس = `10110010`، دکمه A فشرده)

```
بیت‌های اصلی:  1 0 1 1 0 0 1 0 | 1 0 0 0   (۴ بیت آخر = داده، A = 1)
الگوی پالس:   1 0 1 1 0 0 1 0 1 0 0 0
پس از سه‌گانه: [بلند-کوتاه][کوتاه-کوتاه][بلند-کوتاه]...
کد هگز:       0xB2 8   (بسته به ترتیب بیت متغیر است)
```

مقدار دقیق هگز به ترتیب بیت (MSB-first در برابر LSB-first) و اینکه
کدام بیت‌ها اول ارسال می‌شوند بستگی دارد. **RCSwitch کد خام را گزارش
می‌دهد**، پس هگز را مبهم در نظر بگیرید — فقط همان مقدار را بازپخش کنید.

### ۲.۶ شماره پروتکل RCSwitch

RCSwitch پروتکل PT2262 را با **پروتکل‌های ۱ و ۲** شناسایی می‌کند که
در ترتیب بیت متفاوت‌اند. هر دو به همان رشته پالس رمزگشایی می‌شوند،
بنابراین بازپخش با همان پروتکل درست کار می‌کند.

### ۲.۷ سه‌حالته (`f`)

برخی ریموت‌ها از هر سه نماد (`0`، `1`، `f`) استفاده می‌کنند. RCSwitch
به‌طور بومی از حالت سه‌گانه پشتیبانی نمی‌کند — آن را به‌عنوان `0` یا
`1` رمزگشایی می‌کند. **این یعنی بازپخش خام ممکن است شکست بخورد.** باید
رشته پالس دقیق را دوباره ارسال کنید که نیازمند رمزگذار سفارشی است.

> 💡 Flipper Zero از طریق پروتکل `Princeton` خود از حالت سه‌گانه
> پشتیبانی می‌کند. این پروژه فعلاً این کار را **نمی‌کند**.

## ۳. EV1527 / HS1527 (کد یادگیرنده)

**EV1527** یک آی‌سی **کد یادگیرنده ۲۴ بیتی** است. برخلاف PT2262،
**از طریق کلید DIP قابل تنظیم نیست** — هر چیپ یک **شماره سریال
منحصربه‌فرد ۲۰ بیتی کارخانه‌ای** دارد. ۴ بیت آخر، وضعیت دکمه است.

### ۳.۱ ساختار فریم

```
[شناسه ۲۰ بیتی] [۴ بیت دکمه]   → مجموعاً ۲۴ بیت
```

مثال:
```
شناسه:  0xA1B2C    (۲۰ بیت)
دکمه:   0x1        (دکمه A)
فریم:   0xA1B2C1   (۲۴ بیت، هگز)
```

### ۳.۲ زمان‌بندی رمزگذاری

EV1527 از همان **جفت پالس سه‌گانه** PT2262 استفاده می‌کند:

| نماد | زمان‌بندی |
|---|---|
| **0** | کوتاه-کوتاه |
| **1** | بلند-کوتاه |
| **Sync** | فاصله بلند (≈ 31α) |

**همانند PT2262** — فقط تعداد بیت و ساختار متفاوت است.

مقدار معمول α ≈ **۲۵۰ تا ۳۵۰ میکروثانیه**.

### ۳.۳ یادگیری / جفت‌سازی

گیرنده‌های مبتنی بر EV1527 از **«حالت یادگیری»** استفاده می‌کنند:

1. دکمه **pair** گیرنده را ۳ ثانیه نگه دارید
2. ریموت را یک‌بار فشار دهید
3. گیرنده شناسه ۲۰ بیتی را در EEPROM ذخیره می‌کند
4. اکنون ریموت درب را باز می‌کند

**تا ۱۵ تا ۲۰ ریموت** را می‌توان برای هر گیرنده یاد گرفت.

### ۳.۴ پیامد امنیتی

از آنجا که شناسه‌ها **ثابت** و روی گیرنده ذخیره می‌شوند، **بازپخش کد
ضبط‌شده کار می‌کند** — تا زمانی که همه بیت‌ها را درست دریافت کنید. به
همین دلیل این سیستم‌ها برای هر چیز حساس ناامن تلقی می‌شوند.

### ۳.۵ پروتکل RCSwitch

EV1527 به‌عنوان RCSwitch **پروتکل ۱** رمزگشایی می‌شود (همان زمان‌بندی
سه‌گانه). کد هگز از `getReceivedValue()`، همان فریم ۲۴ بیتی کامل است.

### ۳.۶ کلون‌ها

بسیاری از آی‌سی‌های چینی، کلون EV1527 هستند:
- **HS1527** (Hopesun)
- **SC5262** (مشابه اما ۱۲ بیتی)
- **PT4303** (سازگار)
- **XC4388** (سازگار)

همه در زمان‌بندی مشترک‌اند و با هم کار می‌کنند.

## ۵. سیستم‌های کد Rolling (⚠️ پشتیبانی نمی‌شود)

ریموت‌های مدرن (خودرو، درب‌های سال ۲۰۰۰ به بعد، بسیاری از زنگ‌های
بی‌سیم جدید) از **کدهای Rolling** استفاده می‌کنند — مقدار ارسالی
**هر بار تغییر می‌کند**.

### نحوه کار (ساده‌شده، KeeLoq)

1. **ریموت و گیرنده** یک **کلید مخفی مشترک** دارند (در کارخانه نوشته می‌شود)
2. ریموت در هر فشار **یک شمارنده** را افزایش می‌دهد
3. ریموت **شمارنده رمزشده** = `E(key, counter)` را محاسبه و ارسال می‌کند
4. گیرنده رمزگشایی کرده و با شمارنده مورد انتظار بعدی مقایسه می‌کند
5. اگر شمارنده در محدوده **±۱۶** از مقدار مورد انتظار باشد → می‌پذیرد و
   شمارنده را به‌روزرسانی می‌کند
6. اگر خارج از محدوده باشد → رد می‌کند (حفاظت در برابر بازپخش)

### چرا این طرح، Capture-Replay را شکست می‌دهد

- **هر فشار یک کد جدید است** — همان کد را بازپخش کنید، گیرنده رد می‌کند
- مهاجم باید **کلید مخفی** را بداند (AES-128 برای سیستم‌های مدرن)
- حتی یک **جفت ضبط‌شده** (قبلی + جاری) هم بدون شکستن رمز، کلید را
  فاش نمی‌کند

### سیستم‌های متأثر
- **KeeLoq** (Microchip HCS301, HCS200, HCS360)
- **HITAG 2** / **HITAG S** (NXP)
- **AES-128** (ریموت‌های جدیدتر)
- **Somfy** با کد Rolling (خانه هوشمند قدیمی)
- **Chamberlain Security+ 2.0**

### چه کاری می‌توانید بکنید
**با این سخت‌افزار هیچ کاری نمی‌توانید بکنید.** شکستن کدهای Rolling
نیازمند:
- **SDR** (HackRF، RTL-SDR + فریمور سفارشی، یا Flipper Zero)
- **تحلیل کانال جانبی** (تحلیل توان، الکترومغناطیس)
- **ساعت تا هفته‌ها** محاسبه برای طرح‌های آسیب‌پذیر

> ⚠️ **تلاش برای شکستن یک سیستم کد Rolling که مالک آن نیستید، جرم
> کیفری جدی است** (کلاهبرداری رایانه‌ای، سرقت، دسترسی غیرمجاز). نکنید.

## ۷. تشخیص عملی با RCSwitch

RCSwitch با تطبیق نسبت‌های عرض پالس با الگوهای شناخته‌شده، پروتکل را
به‌طور خودکار تشخیص می‌دهد.

### نحوه کار `RCSwitch::available()`
1. یک وقفه، **مدت پالس‌ها** را در یک بافر ثبت می‌کند
2. وقتی **فاصله بلند** تشخیص داده شود، رمزگشایی شروع می‌شود
3. برای هر یک از پروتکل‌های ۱ تا ۱۲:
   - بافر بیت با زمان‌بندی مخصوص هر پروتکل تقسیم می‌شود
   - بیت‌ها به‌عنوان `0` / `1` / `f` طبقه‌بندی می‌شوند (یا رد)
   - اگر **همه بیت‌ها** با زمان‌بندی سازگار رمزگشایی شوند → موفق
4. `getReceivedProtocol()` شماره پروتکل منطبق را برمی‌گرداند

### چرا False Positive رخ می‌دهد
با گیرنده‌های ASK ارزان، **نویز** اغلب شبیه رشته پالس می‌شود:

- **الگوهای بیت تصادفی** ممکن است بررسی زمان‌بندی را با ~۱۲ بیت پاس کنند
- **تداخل** از دستگاه‌های مجاور (Wi-Fi، BLE، منبع تغذیه سوئیچینگ)
- **بازتاب‌ها**ی همان سیگنال (چندمسیری) ممکن است دوبار رمزگشایی شوند

### چطور نویز را فیلتر کنیم

**سمت نرم‌افزار (خودتان بعد از دریافت):**
- کدهای کمتر از ۱۲ بیت را کنار بگذارید
- کدهای با `RSSI:0` (بدون سیگنال AGC) را کنار بگذارید
- کدهایی که فقط **یک‌بار** تکرار شده‌اند را کنار بگذارید — ریموت‌های
  واقعی ۵ تا ۲۰ بار تکرار می‌شوند
- کدهای یکسان متوالی را در یک ورودی ادغام کنید

**سمت سخت‌افزار:**
- از یک **فیلتر Band-pass** استفاده کنید (مثلاً فیلتر SAW برای ۴۳۳.۹۲ مگاهرتز)
- یک **قوطی شیلد** به گیرنده اضافه کنید
- از **روتر Wi-Fi و منبع تغذیه سوئیچینگ** دور بمانید

**تنظیم RCSwitch:**
- `#define RCSWITCH_MAX_CHANGES` (پیش‌فرض ۶۷) — کاهش دهید تا نویز
  فیلتر شود
- `RCSwitch::setReceiveTolerance(60)` — تنظیم حساسیت (۵۰ تا ۸۰)

## ۸. دقت بازپخش — چرا گاهی شکست می‌خورد

حتی برای سیستم‌های **کد ثابت**، بازپخش می‌تواند شکست بخورد:

| علت | توضیح | رفع |
|---|---|---|
| **بیت‌های سه‌حالته** | PT2262 `f` به‌عنوان `0`/`1` رمزگشایی می‌شود | نیازمند رمزگذار سفارشی |
| **ترتیب بیت** | MSB و LSB متفاوت است | هر دو پروتکل را امتحان کنید |
| **عدم تطابق زمان‌بندی** | اصلی ۳۵۰ میکروثانیه، بازپخش ۴۰۰ میکروثانیه | `setProtocol()` را تنظیم کنید یا بازپخش خام پالس استفاده کنید |
| **دریافت ناقص** | برخی بیت‌ها گم شده‌اند (نویز) | دوباره و از نزدیک دریافت کنید |
| **عدم تطابق آنتن** | فرکانس یا طول اشتباه | ۴۳۳ یا ۳۱۵ را بررسی کنید |
| **فرستنده ضعیف** | FS1000A فقط ~۱۰ dBm خروجی دارد | نزدیک‌تر شوید، آنتن بهتر |
| **کد Rolling** | هر فشار جدید است | پشتیبانی نمی‌شود |

### دیباگ بازپخش شکست‌خورده

1. **همان ریموت را ۳ بار دریافت کنید** → مقادیر هگز را مقایسه کنید
   - هر بار همان مقدار → کد ثابت (خوب)
   - مقادیر متفاوت → کد Rolling (پشتیبانی نمی‌شود)
2. **تعداد بیت‌ها را بررسی کنید** → ۱۲، ۲۴ یا ۳۲؟
3. **پروتکل ۱ و ۲ را امتحان کنید** — گاهی یکی کار می‌کند و دیگری نه
4. **فاصله را به ۱۰ سانتی‌متر تا هدف کاهش دهید**
5. **با SDR بررسی کنید** (RTL-SDR حدود ۲۵ دلار است) تا ببینید واقعاً
   چه چیزی ارسال می‌کنید

---

## ۹. ساخت لاگ SDR (توصیه‌شده)

برای پژوهش جدی، از **RTL-SDR** با ابزارهای زیر استفاده کنید:
- **[Universal Radio Hacker (URH)](https://github.com/jopohl/urh)** —
  رابط گرافیکی برای تحلیل پروتکل
- **[rtl_433](https://github.com/merbanan/rtl_433)** — رمزگشای CLI برای
  ده‌ها سنسور تجاری
- **[inspectrum](https://github.com/miek/inspectrum)** — نمایش‌دهنده شکل‌موج

یک‌بار با URH دریافت کنید، پالس‌ها را به‌صورت بصری بررسی کنید، سپس با
NanoSubGHz با همان الگوی بیت دقیق بازپخش کنید. این کار حلقه بین «هگز
ضبط‌شده» و «رشته پالس واقعی» را می‌بندد.

---

## ۱۰. توصیه‌های امنیتی (برای تولیدکنندگان)

اگر در حال **طراحی** یک محصول بی‌سیم هستید و این را می‌خوانید تا
بدانید چه کار نکنید:

1. **هرگز از PT2262 یا EV1527** در محصولات جدید استفاده نکنید
2. **از طرح کد Rolling** با یک رمز واقعی استفاده کنید (AES-128 یا رمز
   سبک تأییدشده‌ای مثل **PRESENT**، **SIMON**، **SPECK**)
3. **احراز هویت دوطرفه** (چالش-پاسخ)
4. **Frequency Hopping** یا **DSSS** در صورت امکان
5. **افزودن nonce/زمان** برای جلوگیری از بازپخش
6. **استفاده از BLE یا UWB** با جفت‌سازی مناسب برای کاربردهای مجاورت
7. **انتشار اطلاعات تماس امنیتی** و آمادگی برای افشا
